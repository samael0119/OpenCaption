## 1. 版本目标

减少短句及句中停顿后的空等时间，提高 CS2 术语和当场实体的识别、翻译一致性，同时精简字幕阅读界面。选择术语库即默认启用场景推断、关联检索、有界上下文和有条件纠正，减少用户输入。保持 Gemma E2B 实时主线、E4B 手动质量档、端侧处理、单个大模型串行推理和有界内存。

先改切分、术语使用和评测，再根据本机配对结果决定是否需要改变模型路线。所有参数均为实验起点，不能作为已实现性能承诺。

### 1.1 整体审查结论与交付边界

方向可行，关键路径是“真实延迟基线 → 分段可行性 → 词库关系正确性 → 自动场景的净收益 → 联合验收”。本版保留用户要求的低延迟、自动场景、词库优化和字幕 UI 四项，但按下面的最小范围交付：

- 分段先做停顿提前提交、5 秒兜底和完整缺口报告；重叠重推及跨窗修订延后。
- 场景辅助先覆盖 CS2 已审核实体、明确别名和地图/战队关系，支持候选、弃权与切换；不承诺自动识别任意赛事或每场比赛。
- 词库治理先修归属丢失、歧义和高频误译，不建设通用知识平台或在线数据更新系统。
- UI 聚焦主字幕、悬浮字幕和术语入口，不扩大为全应用重设计。

每项默认启用的是通过本轮验证的能力；内部依据场景证据和资源预算自动降级，不增加用户必填项。分阶段交付评测包用于验证，完整 v0.2.0 的完成定义仍包含四项；某项失败时应报告未完成，不能以静默关闭代替完成。

## 3. P0：停顿优先、时长兜底的分段

### 3.1 初始策略

采集始终连续，轻量语音检测用于寻找提交边界。先比较能量/噪声底边界与轻量 VAD 的漏语音情况；候选为 Silero 等，实际模型格式、依赖、内存、许可证与 Gemma flavor 集成需单独验证。不能直接把旧 cascade 分段器接上就视为完成。

| 参数 | 实验起点 | 用途 |
| --- | --- | --- |
| 常规提前提交 | 累计约 1.2～1.5 秒后优先寻找停顿 | 减少碎片；这是调度启发式，不是丢弃短语音的阈值 |
| 短答例外 | 检测到短语音后达到同一停顿阈值，即使不足 1.2 秒也可提交 | yes/no、数字、人名不额外等待长静音；是否识别成功由实际短答测试确认 |
| 停顿阈值 | 400 / 600 / 800 ms 对照，先以 600 ms 为基线 | 句中停顿即可提交已有片段，无需等整句话结束 |
| 目标片段长度 | 约 3～4 秒，依据实际处理耗时调整 | 连续讲话中在目标长度附近寻找可靠边界 |
| 最大未提交跨度 | 5 秒作为首轮硬上限 | 无停顿时仍持续出字幕，避免长句一直等待 |
| 边界保护 | 100～200 ms 音节保护，首版保持不重复提交同一采样区间 | 后保护等待计入停顿预算，不能在 600 ms 后再无条件多等 200 ms |

VAD 判断不确定时继续保留音频，并在硬上限提交给 Gemma 判断。尤其不能因解说与观众声能量相近就抑制整段语音。短暂停顿是音频提交点，不保证是完整句末；下一段可携带少量前文帮助续译。

保留固定 5 秒策略作为对照和失败回退。当前 E2E 只返回片段级文本，没有可靠逐词时间戳；仅靠文本相似度难以区分重复音频和真实重复说话。因此 P0 默认 0 重叠，切点分配必须连续且无重复/遗漏。重叠重推和对齐去重归入 P1，先证明其收益和真实重复词保留能力，再考虑启用。

### 3.2 吞吐保护

不能简单改成每 1～2 秒固定调用。已有 Ubuntu E2B 实验平均推理约 2.86 秒/5 秒音频，手机成绩需另测；短片段的固定开销可能使调用频率超过处理能力。

- 保持一份大模型、一个运行任务和一个有界待处理槽。
- 根据近期服务时间、片段提交间隔、队列年龄、替换率及热状态判断负载；RTF 单项不足以描述重叠和短片段开销。
- 过载时优先合并相邻待处理片段，保留时间范围和时长上限；不能无限拼接，也不能合并后突破上下文容量。
- 仍需丢弃时记录准确音频区间和原因，向会话报告缺口；成功句的低延迟不能掩盖遗漏。
- 升温或 CPU fallback 时适当延长目标片段，降低提交频率；不可超过最大未提交跨度而不报告降级。
- 边界后多次回读已推理音频也计入实际算力预算。

实现前明确三个不同上限：**未切分采集跨度、单次推理音频长度、待处理音频年龄**。首轮前两项均不超过 5 秒，待处理年龄上限由 S0 在本机正常与降速回放后冻结，不能用“只有一个待处理槽”代替年龄约束。相邻待处理片段合并后仍须 ≤5 秒；超限时不静默截取，不反复取消在途推理，按明确定义的保留最新策略报告丢弃区间。音频样本、排队副本和合并临时副本都纳入内存预算；PCM 区间所有权和缺口事件须可回放验证。

S0 先测 1～5 秒片段的实际服务时间分布，确定提交间隔与吞吐的可行区间；若本机处理速度不足以同时满足覆盖和低延迟，应保留覆盖证据并报告限制。提前提交不能消除模型本身的处理耗时，也不能保证 P50≤3 秒。

首轮 CPU 实测的 1 秒窗 RTF 中位数 1.726，3 秒窗 0.728，5 秒窗 0.557；因此不采用每秒固定提交，先保留 3～5 秒＋停顿方向。这些参数尚未完成本机联合验收，Android 性能未测。

## 4. P0：让术语库在首次出现和译文检查中生效

### 4.1 当场术语集

将自由文本上下文补充为可选的当场信息：领域、地图、双方队伍、选手/采访对象。允许用户确认和修改；同时加入 4.4 的自动场景推断，手动信息用于优先约束或纠正推断，不依赖联网自动获取赛程。

从全量库选出小的活动词表，而不是向模型塞入全部词条：

1. 已知当场队伍/地图后，相关实体优先；已知队伍的尚未出现选手可以提前获得标准拼写提示。冷启动且没有场景证据时不能保证首次出现即识别正确。
2. 加入少量高频领域术语，如 `eco=经济局`、`utility=道具`、`force buy=强起`。
3. 近期已确认内容用于补充低优先级候选；仅一次模型猜测不能成为新的事实。
4. 按地图/场景筛除冲突译法；无场景证据时保留歧义，避免强制套用。

提示预算按 token 及实际上下文占用控制，分别为实体、术语映射和短前文分配配额。先对照紧凑的 6 / 12 条提示，确认 768 context 下输入和输出均有余量；用户上下文不能挤掉全部术语，也不能靠扩大提示耗尽模型预算。

768 不是全部可用于文本提示的预算：系统指令、音频表示和输出都会受 runtime 的实际容量约束。S0 必须验证固定 0.17.0 API 能否获得 token/容量信息，实测长音频、长提示和 128 token 输出上限的组合；不可假设字符数等于 token 数。不能精确计量时，使用经边界测试的保守模板和长度上限，优先移除原文历史及低相关词条。超限或输出被截断须单独计数，禁止进入反复重试循环；是否调整 context/输出上限应独立对照，不与所有功能同时修改。

容量上限与实际输入长度分别记录。768/1024 在会话准备时选择，逐句通过裁剪检索内容控制实际长度，不反复重建引擎。先保留 768 基线；1024 的质量收益需覆盖本机延迟/内存成本再决定默认。双语协议完整也可能发生中文尾部截断，接近容量的回复需结合计数和内容完整性审计。

把模型任务要求和词表数据分开：任务要求明确“音频出现且语义符合时，优先采用活动词表译法；专名保持标准拼写；不补写词表中未说出的内容”。用户输入和词条仍作为有界数据处理。

首轮结构化场景提示的双语协议通过率仅 2/6，6/12/24 条点位提示均出现只输出中文；简短拼写提示也未稳定通过。S2 先对照注入位置、自然语言格式和任务要求，保持双语覆盖且证明术语净收益后再接入 S2b；不靠扩大解析容忍或补造英文掩盖缺失。Python 0.17 的 tokenizer 已实测，Android AAR 未暴露同等的 Engine tokenize 接口，Android 集成代码先采用本机验证过的保守模板并记录 Conversation token count，当前不运行设备测试。

术语库被显式选择后，默认启用该库支持的全部场景辅助能力，具体默认与迁移规则见 4.6；通用模式仍不注入 CS2。

### 4.2 译文术语检查

对每条完整回复，生成“原文命中、实际提示、建议译法、译文是否符合”的检查结果，保留纠正前后的实验对照。

- 扩展经过人工审核的高频误译规则，保留 `correction_sources`、排除条件、唯一目标和单次替换，拒绝一对多歧义。
- 增加活跃实体的大小写/别名规范化；只有能唯一确定且当前场景支持时才能修改名称。
- 先做规则纠正；无法确定的情况保留模型结果并计入评测，P0 不对每句追加一次大模型调用。
- `save` 在保枪和保存文件中的差异、`plant` 的领域义、地图地点同名等必须有正反例。
- 不根据词库向中文插入原文没有的名称、数字、否定或事件。

英文识别错误、正确英文的误译、中文表达不统一分别统计。词库无法直接挽救所有声学错误；可在低风险范围做活跃实体别名候选检查，但不把任意近音词强制改成人名。

### 4.3 有界语义上下文

每窗新 conversation 的做法暂时保留，显式传入最多 1～2 条已确认原文或结构化实体摘要，标注为“只帮助理解本段，不重复输出历史”。P0 的摘要由选定字段/文本裁剪生成，不追加模型调用。原文前文在暂停、长中断、切场景及代次变化时清空；场景证据按独立的失效规则处理，不能混用两类记忆。

这里的“已确认”仅表示字幕协议完整、已稳定提交，不表示经过人工校对或语义正确；回忆和场景推断都必须允许它出错。

先比较无前文、原文前文和实体摘要，避免错误译文反馈放大。只有质量收益超过提示和 prefill 成本时启用；不默认延续整场 conversation 或累积音频。

### 4.4 P0 增强：自动场景推断与关联检索

用户选择 CS2 术语库后，自动启用“自动识别比赛场景”：从近期双语字幕提取实体及关系，逐步推测当场队伍和地图，再检索相关选手、地图点位与领域译法。手动填写是补充手段，不是自动能力的前置要求。

目标流程：**近期原文/译文 → 实体候选 → 累积场景证据 → 队伍/地图候选 → 相关知识检索 → 下一片段提示与当前译文检查**。

#### 数据底座

现有实体包已包含选手、战队、地图和点位：选手归属记在 `context` 的“战队：…”中，点位归属记在“地图：…”中，可作为迁移起点。它目前是 2026-09-09 快照，不能当作始终最新的阵容。

新建用于应用运行的离线实体关系索引，与开发代码用的 codebase-memory 图谱无关：

| 关系/字段 | 作用 |
| --- | --- |
| 选手 → 战队，生效起止时间、来源、快照时间 | 多个选手共同支持战队候选，避免转会和旧比赛用错阵容 |
| 点位 → 地图，地图版本、通用/特有标记 | 用多个点位共同判断地图，同名点位保留多个候选 |
| 实体 → 原文别名、中文叫法、标准拼写 | 英文 ID、中文名称和解说简称指向同一实体 |
| 术语 → 领域、地图、阵营条件、首选译法/误译 | 结合场景筛选真正可用的翻译建议 |

迁移时把可识别的归属从自由文本转为结构化字段，并人工审核冲突；信息缺失保留 unknown，不能让模型补出未经验证的阵容。第一版随词库发布离线快照，保留版本与来源；在线更新作为后续独立能力，不能阻塞实时字幕。用户看历史录像但日期未知时，阵容关系降低权重，明确说出的队名优先。

选手身份与战队归属独立；快照时间不能冒充转会生效时间。已核实的历史关系按有效区间/比赛范围保存，日期未知或遇到替补/租借时保留多候选与弃权，不把一个 ID 永久绑定一个战队。普通词别名（如 bit/wonderful/frozen）不能单独建立强场景证据。

#### 场景证据与状态

- 从未纠正原文和译文两侧提取候选，英文 ID 和直接报出的地图/队名优先；中文俗称可补召回，但中英来自同一次生成，只计一份证据。
- 首版使用精确别名、词边界和关系查表；模糊/近音匹配只提供低权重候选，不能直接确认场景或改写人名。
- 以最近约 30～60 秒、至多 12 条字幕作有界证据窗口；按音频时间衰减，去除重叠音频、预览修订和同条字幕造成的重复计票。无新证据时也执行过期，不能等下一次命中才清除旧状态。
- 队伍、地图分别维护少量候选及得分；只有证据强度、独立片段/不同实体数量和第一/第二候选差距均满足实验阈值时，才进入“较可信”。评分不伪装成未经校准的概率百分比。
- `Outside` 等常见点位弱支持地图；多个地图指向一致的点位组合支持更强。一个选手 ID 仅支持候选战队，不能直接推出当前对手；需要双方活跃选手/队名以及本场对抗语境。
- “上一张地图”“过去在某队”“昨天对阵”属于历史提及，不应覆盖当场状态。P0 支持明确历史标记和保守弃权，复杂语义无法确定时保持候选。
- 自动状态区分“未知、候选、较可信、有冲突”；新证据推翻旧证据时退回候选，而不是永远锁定。切地图先重置地图证据，保留仍有依据的队伍；暂停/长中断后按中断长度降级或清空。
- 用户明确选择/修改的地图与队伍优先于自动结果，作用域为当前会话；有冲突时提示但不静默覆盖。新会话不自动沿用手动场景，以免下一场比赛被旧约束锁定。

只靠同一个模型的译文存在自我强化风险：某个名称在注入提示后更频繁出现，不能因此自动获得更高可信度。系统无法从最终文本可靠判断某个词究竟来自音频还是提示，因此不能声称可识别“真正独立的声学证据”。记录提示版本后，对已注入的实体设置增益上限，不允许其重复出现独自完成候选确认；不同实体/明确场景陈述仍只是更强的模型输出证据，而不是事实验证。存在冲突、证据过期或持续无新增证据时减弱/退出场景约束，自动回到领域词表。P0 不增加第二模型或隐藏复听来假装解决这一限制。

#### NAVI vs FaZe、Nuke 的示例行为

这是用户给定的假设场景，不声称任何选手当下属于某队：

1. 连续字幕出现多个选手 ID，离线阵容快照分别指向 NAVI 和 FaZe，得到两队候选；若只有一个名字或阵容日期不明，保持待确认。
2. 近期原文出现 `Secret`、`Silo`、`Hut` 等点位，组合支持 Nuke；一句普通的 `outside` 不足以确认。明确说出正在 Nuke 比赛可加强证据，说“上一张 Nuke”则不计当前地图证据。
3. 队伍和地图较可信后，活动词表优先选择这两队相关选手、Nuke 相关点位，以及近期句子涉及的战术术语；保留少量其他候选，避免彻底排除真实的新实体。
4. 后续句子中的 `Secret` 可据已审核的 Nuke 词条采用“地下通道”，`Hut` 采用“黄房”；同时提前提示相关 ID 的标准拼写。语境指向普通词义时，不强制采用地图译法。
5. 若后来出现明确的新地图和对应点位，地图状态降级并重新推断；在旧图知识退出后才启用新图约束，避免两张地图的冲突译法同时注入。

#### 关联检索与翻译接入

第一版采用别名倒排索引、轻量文本相关度与一至两跳关系扩展，无需增加第二个常驻大模型或向量数据库。语义向量检索作为后续候选，只有实测补召回收益成立才加入；专名标准拼写仍依赖实体索引。

推理前排序综合近期已完成片段、当前已知场景、关系距离、知识时效和歧义惩罚；此时尚无当前音频的转写，不能假装能按“当前片段文本”检索。推理后才用当前原文做术语检查和下一轮候选更新。检索只扩展最相关的实体/点位，不把两队全部历史选手和整张地图塞入提示；缺少显式点位邻接数据时不自动推测相邻点位。

保持“短场景摘要 + 精选词条 + 少量原文前文”的输入，和 4.1 共用 token 预算。在新片段开始推理之前固定上下文快照；推理途中产生的旧结果不能修改该片段所用的提示。场景推断在字幕完成后更新并缓存，变化足够明显才刷新，避免每句重新推断或在翻译关键路径追加一次大模型调用。

上下文快照至少携带会话代次、领域/词库版本、场景版本和证据音频截止时间。过期回调不得更新新会话；切库、关闭辅助和场景降级必须同步使待用提示失效。回放中的推理前检索只能使用此前已完成且时间上早于目标片段的证据，不得提前读整段音频的金标或未来字幕。

本方案能影响后续片段，并用于当前完整回复的有条件规则检查；已经展示的稳定历史不自动重译。若要让“当前片段刚出现的新实体”参与同一片段的再次翻译，需要额外文本推理或音频重推，列为 P1 单独测成本，不能宣称零成本改善。

界面简洁展示“推测：NAVI vs FaZe · Nuke（待确认/较可信）”，允许展开查看触发证据、手动纠正或关闭自动识别。证据不足时显示未知，字幕照常运行。

技术参考：[实体联合消歧研究](https://aclanthology.org/D11-1072/)、[检索增强生成研究](https://arxiv.org/abs/2005.11401)。本方案采用实体关联与检索思想，不要求照搬论文的训练流程，也不把其通用任务结果当作本项目性能证据。

### 4.5 P0：术语库质量与结构升级

2026-10-13 对两个本地 JSON 包的静态评估发现：

| 发现 | 判断与本版处理 |
| --- | --- |
| 528 条原始词条按当前英文+中文合并后为 481 条；其中 25 组点位涉及不同地图归属 | 当前合并只并集 aliases，其余字段取优先级胜者；同译法不代表同一地图实体，必须保留各地图的归属/来源 |
| 归一化标准词/别名中有 34 个键指向多个中文译法 | 多义本身合理；补充场景筛选和歧义标记，不能简单删除或取最高优先级 |
| `CT` 可指阵营或警家；`upper` 可指赛事阶段或地图点位 | 普通短词和短别名作为弱证据，完整词组优先，缺少明确语境时不自动改译或确认场景 |
| 基础包有 101 条 alternatives、20 条 avoid，但仅 3 条 wrong_targets；两个包共 6 条包级翻译规则 | 这些数据尚未形成完整的场景约束和纠正规则；审核高频项后转为可执行条件，不能把所有 avoid 无条件变成替换 |
| 实体归属主要为自由文本 context，阵容来自既有快照 | 升级结构化归属、时效和来源；未审核或过期关系只供弱召回，不作为强确认依据 |

本版优先提高可用信息和命中精度，不以扩大词条总数作为目标：

1. **规范 schema 与实体 ID**：区分通用术语、选手、战队、地图和地图点位。地图点位保留 `map_id + callout_id`；同译法可共享显示规则，但不能丢掉所属地图集合。关系有来源与时间，译法有适用条件。
2. **修复合并规则**：按实体和适用范围合并，而不是仅按显示文字；并集可兼容的别名、来源、归属和已审核规则。译法、类别、preserve 或条件冲突进入检查报告，禁止通过优先级静默覆盖。
3. **分层别名**：区别精确拼写、常见口语/中文昵称和易混短词；完整短语、当前场景和语义类别优先。近音/模糊召回只提供候选，不负责自动改名。
4. **完善高频译法**：从真实评测的术语错误出发，首轮审核约 20～30 个高频或高损失条目。每条自动纠正必须同时具备适用条件和反例；数字、否定、人名不进行宽泛字符串替换。
5. **按任务组织检索**：轻量倒排索引分别服务实体发现、地图判定和翻译建议，避免高优先级泛词挤掉当前句的精确词组；词条优先级不等于地图证据强度。
6. **发布前检查与回退**：校验 ID/引用唯一性与存在性、重复归属、别名冲突、过期关系、规则正反例和提示预算；固定词库版本与变更清单。本版只迁移内置包及必要的读取兼容，构建检查拒绝非法包；运行期加载异常时降级为通用能力并显示一次简短状态，不扩大到远程下载/导入/多版本包管理。

补充代表性回归：`A Site` 在多图共享译法但归属完整；`A Main` 随地图选择；`CT` 阵营/警家区分；`upper/lower` 赛事/地图区分；转会/旧录像未知时保持候选；通用采访不受 CS2 词义污染。

### 4.6 P0：选择即生效，手动输入只作补充

- 主流程为“选择音频来源 → 选择任务/术语库 → 开始字幕”，无需再逐项开启动态提示、填队伍、填地图或确认每一次自动识别。已就绪模型和上次有效配置自动复用；系统权限仍按平台要求获取。
- 选择 CS2 后默认运行实体发现、场景推断、关联检索、有界前文和经过验证的术语纠正；未知场景先使用小份通用 CS2 词表，再随证据逐步收窄。
- 自动辅助默认不等于强制采用推测：置信不足、数据缺失或模型预算不足时自动减少约束/回退，字幕正常继续，不弹出阻塞式问答。
- 首页以“CS2 · 自动辅助”概括效果；只有识别出有效候选时展示简短队伍/地图状态。手动补充和场景纠正收进可选详情，不在首页常驻大输入框，不反复邀请填写。
- 设置保留一个统一的“自动场景辅助”退出入口，不要求用户理解检索、证据阈值或逐项开关。实验开关保留在诊断配置中，不进入普通用户主流程。
- 新版新增独立的辅助偏好字段：选择领域时缺省为自动开启。升级不把旧 `autoTermHints=false` 自动迁移成“全部辅助关闭”，因为旧代码每次保存都会写该布尔值，无法可靠判断是否主动关闭。新版明确关闭的偏好按领域保存，后续启动继续尊重；用户可以主动重新开启。
- 从 CS2 切到通用或其他库时清除该领域推断和提示，异步旧结果不能重新注入；结束会话清除本场证据，领域选择偏好仍可保存。每个库按声明的能力运行，不能在缺少实体关系的库上假装支持战队推断。
- 按语音任务裁剪能力：纯转写不执行翻译纠正；自动语言任务只对支持的语言/别名进行实体检索，未支持时保持原文和通用翻译。关闭统一辅助后停止动态场景/前文/关联提示并清空自动状态，保留用户选择的领域和静态基础术语能力，界面说明为“仅基础术语”。

## 5. P0：字幕 UI 精简与视觉优化

### 5.1 评估结论与范围

本轮查看了 [现有字幕截图](images/captions.jpg)、[首页截图](images/home.jpg) 和当前 `lib/main.dart`、原生 `PlaybackCaptionService.kt`。截图作为既有视觉参考，不代表本轮已运行或验证新界面；当前代码仍使用逐条 Card、音量条、可展开状态栏和黄色/绿色字幕。

主要改进空间是阅读层级、留白和信息密度：状态摘要包含推理/CPU/GPU等指标；展开详情会占用字幕空间；每条卡片重复背景和内边距；首页重复解释模型/处理方式，并显示上下文输入和动态提示选项。主界面还直接使用为暗色悬浮窗设计的固定前景色，需要独立验证浅色主题的对比度。原生悬浮窗使用矩形底板、常驻字号按钮和最多 8 行的 TextView。

本版做现有界面的聚焦优化，范围为字幕页、悬浮字幕以及首页的术语/上下文入口；保留 OpenCaption 品牌、青绿色强调色、系统字体、Material/Android 常见操作。高级感通过排版、比例、对齐和克制的状态反馈体现。暂不重做模型下载管理等完整页面。

### 5.2 建议布局与交互

| 区域 | 本版方案 |
| --- | --- |
| 顶部 | 紧凑显示“收音中 / 已暂停”和音频来源；收音活动融入小指示器，避免大进度条使人误以为是识别进度 |
| 场景 | 一条可点开的辅助信息，如“CS2 · NAVI vs FaZe · Nuke（推测）”；未知时仅显示“CS2 · 自动辅助”，不常驻未知字段列表 |
| 字幕正文 | 以连续阅读流替代重复的厚卡片，用间距区分片段；双语任务中文为主、原文为辅，建议中文 24～28 sp、原文 14～16 sp，按用户字号及系统缩放调整 |
| 当前片段 | 仅用轻微背景层次或细标记区分最新内容；历史保持可读，不通过过低透明度淡出。已确认内容不逐字闪烁 |
| 控制区 | 固定在底部安全区，暂停/继续为主要操作、结束为次要操作；“回到最新”只在离开跟随时出现，不挤压正文 |
| 诊断 | 推理耗时、CPU/GPU、队列和内存移到按需打开的详情；温升、权限失效、音频缺口等需要行动的状态直接显示 |
| 首页 | 术语选择即说明自动辅助生效；补充上下文收进可选详情，合并重复的模型/任务说明，清晰保留开始字幕和缺失模型提示 |
| 悬浮字幕 | 同一套中文主/原文辅排版，紧凑底板和一致圆角；保留可发现的拖动与停止入口，字号/透明度进入简短菜单，避免控制栏长期占据大量视频画面 |

双语阅读默认突出中文；纯英文/纯中文任务以对应原文为主，不出现空占位或翻译等待。用户已有语言显示、字号和颜色选择保持可用。主界面默认颜色随浅/深色主题适配，暗色悬浮窗单独校验，避免一套固定颜色兼用所有背景。

长字幕自动换行，主界面不截断稳定正文；悬浮窗需明确最大可见高度和长内容展开/回看方式，不能静默裁掉末尾。小屏、横屏、系统大字和长队名时，场景行和工具栏可折行/收起次要内容，优先保住字幕正文与停止操作。

保持 150～200 ms 的轻量状态/滚动过渡，不增加字幕展示等待；用户浏览历史时不抢滚动位置。采集无声音、正在生成、暂停、结束、译文不可用和音频缺口采用简短可行动文案，状态不能只靠颜色表达。预览动效仅在第 6 节协议完成后接入。

技术参考：[Android 无障碍交互目标建议](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views)要求至少 48×48 dp 可点击区域；[Flutter 文本与缩放](https://docs.flutter.dev/ui/design/text)用于实现大字适配。圆角/字体初值是待验证设计参数，不是通过截图质量验收的结论。

### 5.3 实施与验证

先建立浅/深色主字幕页和视频背景悬浮窗的静态布局，用现有真实字幕覆盖短句、长句、人名和错误状态，再接入实时状态；不依赖 AI 插图、远程字体或持续模糊/复杂特效。拆出字幕片段、场景摘要和控制区组件，按需局部刷新，避免音量/诊断频繁更新带动整页重建。

本版验收检查浅/深色、小屏/横屏、系统大字、长字幕、纯转写、错误/暂停、手动回看/回到最新、悬浮移动/停止和自动场景变化。文本对比度、TalkBack标签/阅读顺序、48 dp触控区域、长内容完整性和字幕实际展示时间必须检查；记录界面卡顿，不以动画或延迟刷新换取漂亮截图。实施时先一次集中视觉检查，再批量修正并确认，避免无界抛光。

## 6. P1：预览字幕和有限修订

P0 验收后再做这一层，避免同时改变切分、协议和字幕稳定性。

LiteRT-LM 上游 Kotlin API 提供 `sendMessageAsync` 的流式输出；它支持输出逐步返回，不能据此认定模型已经支持持续音频输入或增量声学缓存。需核对项目固定的 0.17.0 包、MTP 共存、取消和异常回调。

- 仅对当前未确认字幕显示预览；中文要等有可读内容再展示，不把半个协议标签显示给用户。
- `BilingualEvent` 增加稳定 ID、revision、预览/最终状态，并同步生成 Pigeon 桥接文件。
- 英文预览和中文首条分别计时，不能用提前显示英文代替中文延迟达标。
- 后续音频补全时，仅允许修订当前未确认片段；已确认历史保持稳定，原有延迟门槛按稳定中文计算。
- 流式输出和跨窗音频重推分别评测；重推通过同一推理 worker，不能增加第二份大模型。

技术依据：[LiteRT-LM Kotlin API](https://github.com/google-ai-edge/LiteRT-LM/blob/main/docs/api/kotlin/getting_started.md)；VAD 边界参数参考 [Silero VAD 源码](https://github.com/snakers4/silero-vad/blob/master/src/silero_vad/utils_vad.py)。上游 main 的能力不等于当前固定版本已经通过验证。

## 7. 评测与验收

### 7.1 先建立可靠对照

同一批音频和金标串行对照：A 当前 5 秒固定窗；B 只改停顿切分；C 只改活动词表；D 两者结合；前文和流式预览另设单变量实验。比较提示时固定模型、任务、领域、切分、线程、MTP 和 context。

自动场景专项对照：固定切分条件下比较“无场景、手动真实场景、自动推断场景”；手动真实场景是理想信息对照，不保证一定优于自动方案。另注入一次错误选手 ID/误译，验证场景能否弃权、纠错，且不会持续强化错误。测试历史录像、转会、替补、回顾旧比赛、跨图同名点位、地图切换、长停顿和未知阵容。

回放器必须采用与 Android 相同的因果分段规则，只看当前和过去音频。已有 `quiet_cut_ms` 会读取目标边界之后的音频，不能把这种离线边界选择直接当作实时延迟改善。统一或通过固定 PCM fixtures 验证两端切点、收尾和时间戳。

现有 clip 已被多轮实验使用，继续用于开发诊断；最终验收补充未参与调参的说话人/场次。测试素材覆盖：短答、句中 300～1200 ms 停顿、无停顿长句、跨界人名/术语、弱声/口音、观众声、静音音乐、地图歧义、否定/数字和运行降速。

场景评测以连续会话而非打散句子为单位：每段从未知状态启动，并包含场景切换。按比赛/说话人隔离开发与保留集；固定数据版本、样本清单、切点规则、配置、模型 SHA、冷/热状态和重复次数。S0 建立可用素材与标注清单，至少具备两种地图、多个队伍组合、一次切图和一次回顾旧比赛；不足时先完成开发验证，不宣称泛化通过。模型推理仍串行、有明确内存上限。

### 7.3 v0.2.0 开发预览版的具体决策门槛

上表 P50≤3 s、P95≤6 s、质量≥90% 等来自既有正式发布目标，当前基线尚未证明达到，不能作为本版必然兑现的承诺。本版开发预览先按同设备配对比较判断改进，并如实列出距离正式目标的差距。首轮候选门槛如下，S0 在看候选结果前冻结评测口径；需要调整时记录原因并使用新的保留集：

| 关口 | 通过条件 |
| --- | --- |
| 分段 | 在预先标注的有停顿样本上，稳定中文 P50 相对固定窗改善 ≥20%；全样本 P95 不退步超过 5%；成功覆盖率不下降，短答/弱声不新增系统性漏句 |
| 自动场景 | 在未调参连续会话中，“较可信”地图和队伍对的准确率分别以 ≥95% 为目标；同时报告全时长正确覆盖与弃权，不能通过全部弃权达标。对知识覆盖且证据充分的场次，至少 80% 在首个充分证据点后 30 秒内形成正确状态；“充分证据点”由人工标注，不能由算法自己定义 |
| 场景恢复 | 固定的错误注入/切图用例中，出现明确冲突后的 2 个已完成片段内解除错误的强场景约束；允许回到未知，不要求立即猜中新场景；后续计时同时报告音频时间和实际展示时间 |
| 术语净收益 | 对基线中的可纠正术语/实体错误，候选在保留集减少至少 20%；同时报告新增错误，关键否定/数字不新增错误，已定义的歧义反例不得误改。若基线错误样本过少，补素材而不是用百分比宣称提升 |
| 性能与资源 | 同设备/模型下记录检索、上下文额外 prefill、队列丢弃和峰值内存；联合方案须满足分段覆盖/延迟门槛，且不得新增 OOM、持续积压或热降级失控 |
| UI 与默认行为 | 四种语音任务、辅助默认/关闭/切库、主题/大字/长字幕/悬浮控制用例通过；字幕实际首显不因动效等待，历史回看位置稳定 |

准确率报告样本数、分母和不确定性；一个连续会话的数百条字幕不能假装为数百个独立比赛样本。实验开发包可以早于全部门槛交付，但完整 v0.2.0 开发预览仍需上述验收与 3×60 分钟长稳，并列明未达到的正式发布目标。

## 8. 实施顺序与交付

### 8.1 大模型实现工作量口径

以**可验收工作包数量 + 开发模型 token 消耗 + 实验资源量**衡量工作量，替代人工工作日。一个工作包指一个可独立检查的“读取相关代码 → 实现或实验 → 验证 → 必要修复”闭环，不等于一次聊天回复、一次 API 调用或一个提交。

下表 token 是从本计划实施开始计算的粗略增量估算，包含代码探索、实现、测试输出分析、评审、文档与常规修复；不包含已发生的规划对话。它是规划预算，不是测量结果，也未设置实际执行硬上限。假设复用当前仓库与已有模型环境、按相关范围读取代码、控制工具输出并及时保留阶段摘要；更换执行模型、长上下文重复输入和重大返工都会改变消耗。当前缺少同项目完整实现的 usage 基线，置信度低，S0 后必须校准。

统一按各次开发模型请求的输入与输出 usage 累计：重复携带的上下文每次都计入；缓存命中部分计在输入中并单独列示，不再重复相加。推理 token 按实际提供方口径归入输出或独立列示，避免双计；无法获得的 usage 标为未知，不能从文件字数或最终回复长度假装推算实际总消耗。该总量不能直接换算费用或账户额度。

### 8.3 实验与数据资源另行计量

开发模型 token 与本机运行 Gemma 的资源分开记录：

- 音频回放量按“素材总分钟数 × 配置数 × 重复次数”登记；A/B/C/D 至少四种配置，场景专项与边界实验额外列出，不把所有组合做无界笛卡尔积。CPU/GPU 推理耗时用实测 RTF 与启动开销估算，并记录实际运行时间和峰值内存。
- 长稳仍需 3 次 × 60 分钟的真实运行与日志检查；模型等待、构建等待和本机冷却不会自动等价为开发 token，只有后续读取/分析进入模型上下文才产生相应 token 消耗。
- 素材与质量审核按已标注音频分钟数、审核关系条数、术语正反例数、连续场景用例数记录。首轮 20～30 个高频词条至少各有适用例和反例；必要的人工金标/事实审核是验收依赖，不能用 token 预算代替正确性证据。
- 全量历史阵容核查和在线知识更新属于后续范围；现有范围需要的关系审核、本机验证与必要修复已包含在工作包中，外部数据缺失单列依赖与影响。

S1、S2、S2b 各自保留诊断开关以隔离回退；完成后同步 PRD、design、评测说明、CHANGELOG 和版本号。

依赖顺序：S0 → S1；S0 → S1b → S2 → S2b；S2c 的静态阅读布局可先做，场景状态接入依赖 S2b；S3 在各分支通过专项门槛后进行。S4 不阻塞 v0.2.0。先交付分段对照包，再交付场景/词库对照包，最后进行 UI 与全部默认能力的联合验收，以便定位性能或质量回退。
