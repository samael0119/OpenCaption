# 第二轮：真实节奏回放，而非离线处理后推算

## 可用性目标（项目建议验收线，不是行业标准）

当前 Ubuntu 数据不能直接等同于小米 15 性能；采访还需要采访音频验证。

| 指标 | 普通采访试用目标 | 快速比赛解说目标 |
|---|---|---|
| 稳态处理实时因子 RTF | ≤0.8，理想≤0.7 | ≤0.7，留出突发长句余量 |
| 片段结束至字幕 P95 | ≤5 秒 | ≤3 秒 |
| 约 3 秒片段的推理 P95 | ≤3 秒 | ≤2 秒 |
| 队列等待 P95 | ≤1 秒 | ≤0.5 秒 |
| 丢段 | 正常负载为 0；过载必须披露 | 同左，不通过丢内容达标 |
| 非静音段有效双语输出 | ≥98%，但不能冒充准确率 | 同左 |
| 人工语义抽查 | ≥95% 关键命题正确；人物、武器归属、否定等严重反转为 0 | 同左，并检查快节奏信息遗漏 |
| 持续运行 | 至少 30 分钟无卡死/崩溃、内存不持续增长 | 同左，加上温控降频测试 |

RTF = 全部推理耗时 / 原音频时长。仅在无丢段时可以用来判断完整内容的吞吐余量。3 秒片段若需 3 秒推理，虽然平均勉强跟得上，也没有余量承受更长输出。不要用文本 decode tok/s 代替音频编码、prefill、decode 完整耗时。

即使片段结束后 2 秒出字幕，片段开头的词也已经等了约 5 秒。低能量切点额外需要最多约 600 ms 的观察延迟（先看到 target+300ms，再可能切回 target−300ms），不应从延迟统计里扣除。

## 实验实现与安全边界

- 每 20 ms 从同一 WAV 按真实时间读入 PCM，缓冲仅保留未切片音频和可选重叠；不整段载入内存。
- 一个驻留 Gemma/LiteRT-LM、一个当前任务、一个待处理槽；处理不过来时替换待处理段并记录 `dropped`。不自动重试，不并发模型，不增加 ASR。
- 实验组 target=3000ms，在 ±300ms 中寻找相对低能量的 20ms 帧。若没有明显低点，按 target 切；不等待静音、不判断“收音是否完成”。实际片段上界小于 4 秒。
- 使用原始 PCM，仅改变切点；没有声源分离/降噪，低能量不是可靠的人声或句尾分类器，枪声后低点也可能被选中。
- EOF 余音不静默丢弃；后续已补充保护：尾段提交不替换一个完整待处理段。极短尾段仍可能产生幻觉，需单独审查，不能当作普通整句评分。
- 外层 cgroup 物理内存上限 4 GiB、禁 swap；后续运行增加默认 1800 秒总任务 watchdog，超时终止整个评测。它不是每段推理超时恢复，也不证明 Android 已解决卡死。
- 记录输入时间、切点原因、ready、排队、推理、输出时间、峰值 RSS、采集迟到、丢段和错误。初始化单独计时；文件预先规范化，不计入实时采集链路。

## 可复现命令

依次执行，不同时加载多个引擎：

```bash
scripts/run-gemma-eval /home/hyh/Downloads/clip.wav --realtime --window-ms 3000 --overlap-ms 0 --threads 4 --output evaluation/results/rt_fixed3.jsonl
scripts/run-gemma-eval /home/hyh/Downloads/clip.wav --realtime --adaptive-cut --window-ms 3000 --overlap-ms 0 --threads 4 --output evaluation/results/rt_adaptive3.jsonl
python3 evaluation/audit_realtime.py evaluation/results/rt_fixed3.jsonl evaluation/results/rt_adaptive3.jsonl
```

两组均无当场 hints，128 输出 token、1024 context token、无思考；仅改变切片策略。不与上一轮 2 线程/500ms overlap 的实验直接归因比较。

解析候选保留为独立 `protocol_candidate.py`，离线审查相同 raw 输出，避免重新推理带来混杂。可以恢复无标签的明确 EN+ZH 两行，并拒绝无汉字的伪中文；不意味着译文正确。未修改 Android 默认策略。

## 本轮完成结果

同一 120.014 秒文件，各配置独立初始化，依次运行；每个配置目前只测一遍，时间上的小差异不能宣称统计显著。

| 配置 | 段数 | RTF | 推理 P95 | 片段结束→输出 P95 | 片段开始→输出 P95 | 旧解析有效 / 候选解析有效 |
|---|---:|---:|---:|---:|---:|---:|
| 固定 3 秒、无提示 | 41 | 0.862 | 3.30 秒 | 3.69 秒 | 6.69 秒 | 24 / 38 |
| 低能量切点、无提示 | 40 | 0.892 | 3.45 秒 | 4.44 秒 | 7.41 秒 | 27 / 40 |
| 固定 3 秒、少量比赛提示 | 41 | 0.822 | 3.40 秒 | 3.53 秒 | 6.50 秒 | 9 / 27 |

三组丢段和推理异常均为 0，峰值 RSS 分别为 1965.9、1990.8、1953.9 MiB；采集线程最大迟到分别 14、11、36 ms。约 13ms EOF 尾段在两组固定窗中单独计数，不能把它等同于完整有声语句。低能量组没有这个超短独立尾段。表内时延包括被解析拒绝的推理结果，不等于有效字幕时延。

少量提示配置的完整字符串：

`Match: Spirit vs MOUZ, Dust2. Names: donk, sh1ro, tN1R, zont1x, torzsi, xertioN. Terms: scout=鸟狙; headshot=爆头; cat=A小; CT=防守方; numbers advantage=人数优势.`

这组只改变 prompt hints。尾段防替换保护和 watchdog 在第三组运行前加入；前两组没有队列替换，所以没有实际生效的队列策略差异，但复测仍应统一版本。

### 内容抽查与晋升决定

- 固定窗出现 `Dako fine → 达科很好`、`numbers on spirit → 对精神有数字`、`Pressing mouse → 按鼠标`；格式正确不代表内容可用。
- 低能量组能恢复全部 40 个双语格式，但仍把 sh1ro 听成其他名字、把人数优势译成数字、把 MOUZ 译成鼠标。延迟更差，**不晋升默认切片策略**。
- 提示组有一处 scout 正确译为鸟狙，但另一处仍为侦察兵；有更多只有中文或缺字段的结果。较低 RTF 可能包含少输出的影响，**不认定速度/质量正向，不晋升这条提示**。
- 独立解析候选恢复无标签双语，固定组从 24 到 38；属于格式兼容收益，**仍处于本地候选，未迁移 Android**。需要更多无语音/乱码/解释性输出验证误接收风险。
- 独立术语候选仅在 `just a scout`、`shot out of the scout` 等明确武器短语、单个英文 scout、单个中文“侦察兵”同时成立时替换为“鸟狙”。无提示固定组命中 2 处，提示组 1 处；这些是同一素材的重复证据，不能当作 3 个独立质量样本。它修正武器词但未修正“射出鸟狙”这种句法错误，因此**不宣称整句变得正确，暂不写入产品术语库**。

### 下一轮优先级

先把完整双语输出和语义质量提升到可用水平，再压窗口。只在本地比较少量 prompt 变体、4–5 秒更完整上下文和相同参考片段；逐项控制变量，避免同时加入多个纠错规则。采访需要新增真实采访素材，不能从这一段比赛解说直接推断采访准确率。手机是否卡死、温控降频是否过载仍须最终真机复验，本地不能保证不再出现异常。
