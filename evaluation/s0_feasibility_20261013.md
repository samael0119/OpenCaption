# v0.2.0 S0 第一轮可行性验证

日期：2026-10-13。结论：**停顿分段与轻量关系检索值得继续；现有提示注入不够稳定，不能直接作为默认场景辅助上线。** 本轮是 CPU 开发实验，S0 的 Android 性能与展示延迟验证尚未完成。

## 1. 条件与范围

- 本机 CPU 标识 AMD Ryzen 7 8845H，可见逻辑 CPU 8 个，Gemma/音频编码均设置 4 线程。
- LiteRT-LM Python 0.17.0；Gemma E2B，SHA-256 `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c`。
- MTP 开启、context 768、最大输出 128 token、temperature 0、thinking 关闭、CPU memory cache。系统指令按 Android CS2 模板组织，复用现有双语解析器。
- 三次模型装载分别做 1 次离线 warmup；累计 **98 次计入结果的推理 + 3 次 warmup**。始终串行，只驻留一份 Gemma；未同时加载 E4B。
- Gemma 使用 cgroup `MemoryMax=6144M / MemoryHigh=5376M / MemorySwapMax=0` 和每轮 900 秒总超时；VAD 使用独立 512 MiB cgroup，在 Gemma 装载前完成。
- 素材为本机四个 WAV，总计约 299 秒；`clip.wav` 有既有双语 SRT，其余素材没有本轮新增的逐句人工金标。它们是开发素材，不能作为独立保留集。
- ADB 检查没有已连接设备；没有测试手机 GPU、Android VAD 集成、UI 首显或长稳。

实验包含：1～5 秒服务时间曲线；完整 clip 的 5 秒固定窗/600 ms 停顿窗对照；已知场景提示对照；6/12/24 条点位提示；短前文/容量压力；历史 NAVI–FaZe/Nuke 片段；5% 音量片段和精确全零输入；三种拼写提示布局。

## 2. 分段可行性

Silero v6.2.1 ONNX，SHA-256 `1a153a22f4509e292a94e67d6f9b85e8deb25b4988682b7e174c65279d8788e3`；ONNX Runtime 1.22.1、单线程 CPU。按官方接口使用 512 新样本、64 样本历史和循环状态，采集调度每 20 ms 只消费已经完成的 VAD 帧。[官方接口实现](https://github.com/snakers4/silero-vad/blob/v6.2.1/src/silero_vad/utils_vad.py)

VAD 全部处理约 1.319 秒，约为素材长度的 0.44%。这说明本机预处理开销很小，尚不证明 Android 上的内存、耗电和集成成本。

| 素材 | 音频秒数 | 5 秒固定窗数 | 600 ms 停顿窗数 | 提前停顿提交次数 |
| --- | ---: | ---: | ---: | ---: |
| clip：持续解说 | 120.014 | 25 | 26 | 5 |
| NiKo 采访 | 66.002 | 14 | 15 | 2 |
| 比赛 demo2 | 65.013 | 14 | 17 | 8 |
| 历史 Nuke demo3 | 48.007 | 10 | 12 | 5 |

同时生成了 400/600/800 ms 切点。持续解说的 600 ms 方案只触发 5 次提前切分，其余主要仍依赖 5 秒兜底，因此不能期待 VAD 消除所有长句延迟。

所有策略保持首尾和相邻采样区间连续，零重叠、不丢弱声/静音 PCM；VAD 只决定提交点，不决定删除音频。7 个测试覆盖非整帧尾部、未来数据不能改变已提交边界、短答例外、静音保留、跨图归属、歧义和通用地图词汇不冒充地图名称。测试通过仅证明这些程序约束，不证明 VAD 语音召回率或真实短答识别正确。

## 3. Gemma 的短窗与吞吐

每档 3 个起点：解说、采访和 Nuke 片段。短窗为同起点的不同长度前缀，并非人工挑出的完整句子。

| 音频长度 | 推理耗时中位数 | 中位 RTF | 解释 |
| --- | ---: | ---: | --- |
| 1 秒 | 1.726 秒 | 1.726 | 连续每秒提交会跟不上 |
| 2 秒 | 1.919 秒 | 0.960 | 余量很小；其中一个样本耗时 4.122 秒 |
| 3 秒 | 2.185 秒 | 0.728 | 有一定吞吐余量 |
| 4 秒 | 2.782 秒 | 0.696 | 比 3 秒更少调用，但采集等待更长 |
| 5 秒 | 2.787 秒 | 0.557 | 吞吐更稳，固定采集等待仍较大 |

首次装载约 21.234 秒；各次装载及 warmup 与稳态推理分开。计量中的峰值 RSS 约 2.302 GiB，低于本轮 6 GiB cgroup 上限；RSS 不是整个系统/cgroup 的完整内存占用。

**建议**：以 3～5 秒目标窗配合停顿提交继续试验，不采用每 1 秒固定推理。2 秒也需要队列与热状态保护。样本少且没有实时捕获竞争，不能把本机曲线当作手机参数或 P95 保证。

## 4. 完整音频的质量对照

同一份 120.014 秒 PCM，无提示辅助，使用全部 407 个金标英文词计算交付英文 WER；解析失败计入遗漏，未使用宽松恢复补回英文。

| 指标 | 固定 5 秒 | 停顿 600 ms＋5 秒兜底 |
| --- | ---: | ---: |
| 双语协议有效窗口 | 21/25 | 24/26 |
| 有效且非“译文暂不可用”的中文窗口 | 20/25 | 23/26 |
| 推理中位数 | 2.771 秒 | 2.684 秒 |
| 推理 P95（本轮窗口） | 3.932 秒 | 3.924 秒 |
| 全素材推理服务时间合计 | 69.599 秒 | 71.858 秒 |
| 交付英文 WER | 32.43% | 29.24% |

停顿切分英文 WER 改善约 3.19 个百分点，同时略增加总推理工作量。固定窗包含约 13 ms 尾段；本探针保留所有 PCM，而当前 App 对不足 1 秒收尾有不同处理，因此本表不是对现有 APK 的严格复现。

此处“协议有效”不等于语义正确或成功句覆盖率。金标中既有不确定 cue 25，本表没有排除它；不同切分的窗口也不能一对一当作独立样本。中文语义、数字/否定和实体标准拼写仍需人工审核。

本轮串行离线请求并非按真实音频时钟播放，**没有得到端到端字幕 P50/P95**，也未证明计划中的延迟提升 20% 门槛；不能用推理耗时下降约 87 ms 代替采集等待改善。

## 5. 提示与容量：当前主要风险

在固定音频、同一模型与参数下，已知场景对照使用 Spirit/MOUZ/Dust2、选手拼写和少量术语映射。它使用人工已知信息，是信息对照而非自动场景结果。

- 原无提示的这 6 个片段均得到双语协议；加结构化场景/术语提示后仅 **2/6** 得到双语协议，其余主要只输出中文，缺少英文。专名也未稳定变成标准 ID。
- Nuke 点位的 6/12/24 条提示各测试一次，**0/3** 通过双语协议。会话计数为 391/421/493，远低于 768，说明失败不能全归因于容量不足。
- 另有“12 条词表＋两条短前文”的单次样本通过，会话计数 469；它只证明一个组合能运行，不足以选为默认模板。
- 极长提示的粗略文本 token 数 612，会话计数触达 **768**；输出只剩英文半句，缺少中文。仅生成约 15 个文本 token 即结束，说明不能只盯 128 输出上限判断截断。

进一步做 3 个相同音频片段、3 种提示布局：

| 布局 | 双语协议通过 |
| --- | ---: |
| 无额外提示 | 3/3 |
| system 中简短 `Name spelling hints` | 2/3 |
| user 文本中简短拼写提示 | 1/3 |

简短自然语言格式比本轮结构化混合提示更稳，但仍未达到可默认开启的门槛。没有观察到稳定的标准选手 ID 改善。P0 必须先验证“精简格式、明确双语要求、按任务分配提示”的组合，而不是增大词库或放宽解析来掩盖英文缺失。

Python 0.17 的 `Engine.tokenize` 和 `Conversation.token_count` 已实测。检查项目固定 Android 0.17.0 AAR 的公开 JVM API，发现 `Conversation.getTokenCount` 和 `sendMessageAsync`，但 `Engine` 没有公开 tokenize 方法。这是静态符号检查，不是手机调用验证；Android 需要先用本机模板计量/保守长度上限，并接入会话计数诊断，不能照搬 Python 的预请求计量接口。

## 6. 自动场景与词库

本轮只做实体关系/别名检索原型，未实现生产级时间衰减、置信门槛、历史提及识别或错误恢复。

- 保留原始地图关系后，`A Site=A包点` 能保留 7 张地图归属，证明无需新增大模型即可修复当前合并造成的信息丢失。
- 人工输入 `Secret/Silo/Hut` 可召回 Nuke 关系；这是字典功能测试，不是从音频自动识别成功。
- 历史 Nuke 片段的实际模型英文中，原型召回 Nuke 5 类点位、Cache 4 类、Anubis 1 类，以及 NAVI/FaZe 候选。许多点位跨图共享，普通动词/名词也能触发词库，不能凭最高票立即确认。
- `b1t` 的别名 `bit` 会从另一段 Spirit/MOUZ 解说中的普通词触发 NAVI，形成假候选；`headshot`、`hell` 也不能简单作为地图强证据。
- 用户素材说明将历史片段标为 2025 年 NAVI/FaZe 比赛；当前快照把 karrigan 关联到 Falcons，检索不到 broky。未知日期时按当前阵容硬推会出错，原型不能保证自动确认正确的双方。
- 基础包的 `category=map` 还用于通用词 `bombsite`。已在实验原型中区分真正地图实体，避免把“包点”当成地图名称；生产 schema 需明确区分地图与地图相关词。

**建议**：继续轻量关系索引；先治理归属、类别、弱别名和时间信息，再加入多证据候选与弃权。地图可能比战队对更容易判断，但本轮还没有独立的准确率/覆盖率成绩。自动辅助产品入口保持计划中的“选择即启用”，实际启用模板和强约束须先通过专项门槛。

## 7. 静音、弱声与未完成项

5% 音量的一个 5 秒片段仍返回双语协议，但名称未正确识别；这不是弱声质量验收。精确全零的 1 秒输入返回混合格式的 `[NONE]`，解析器拒绝为字幕；当前 App 本来就会在进入模型前跳过精确全零，不能据此推断音乐/观众声零幻觉。

未完成项：Android GPU/CPU 服务曲线、VAD 在 Gemma flavor 的接入、音频时钟/展示时钟、实时队列与热状态、两图多队连续会话的保留集、提示专项、中文语义/否定/数字人工审核、UI 动态验证及 3×60 分钟长稳。本轮没有冻结最终门槛或宣布 S0 全部通过。

## 8. 对实施顺序的调整

1. 可进入 S1 的因果分段与诊断实现，保留 5 秒回退，先不加重叠；手机参数仍待验证。
2. 并行于逻辑依赖的下一项是 S1b 词库治理，优先修地图归属、类别和短别名。此处指工作顺序可独立，不要求并行加载模型。
3. S2 增加提示协议专项退出条件：同音频配对测试需保持双语覆盖且有术语净收益，未通过则继续试验，不接入更强的自动提示。
4. S2b 保留为候选/弃权机制，不能把当前静态检索原型视为完整比赛识别。
5. S2c 的静态阅读布局可以推进；S0 不把截图或符号检查当成手机运行成绩。

完成约 4 个实验工作包。开发模型 usage 在本轮工具中不可获得，标为未知，暂不能用 98 次本地 Gemma 请求校准计划中的开发 token 预算；两者是不同消耗。
